## Build from source

Developer requirements: Node.js 24, .NET 10 SDK, Windows for native tests/publishing. End users need neither Node nor the .NET SDK.

```powershell
npm ci
npm run lint
npm test
npm run build
dotnet test companion/tests/SoundpadWeb.Tests.csproj -c Release
dotnet build companion/harness/SoundpadWeb.Harness.csproj -c Release
npx playwright install chromium
npm run test:e2e
# Safari's engine, as CI also runs it:
npx playwright install webkit
$env:TEST_BROWSER='webkit'; npx playwright test --output test-results/webkit
dotnet publish companion/SoundpadWeb.Companion.csproj -c Release -r win-x64 --self-contained true -o artifacts/release
```

`dist/` is the fully static website. `artifacts/release/SoundpadWeb.exe` is the standalone executable. The normal Windows workflow builds both and uploads them. Linux can build/test the frontend and publish Windows code with suitable targeting, but native pipe/image tests require Windows.

For development, run `npm run dev`, then:

```powershell
.\artifacts\release\SoundpadWeb.exe --dev --site http://127.0.0.1:5173/
```

This connects to real Soundpad if running. Routine browser tests instead launch a completely separate mock pipe via `companion/harness`; fixtures never ship in the EXE. Optional real Nostr/WebRTC browser integration tests: `$env:LIVE_RELAY='1'; npm run test:e2e -- --grep 'live Nostr'`. They still use a mock Soundpad, so no real audio plays. CI's default tests do not depend on public relay availability, and since 2.41.0 they do not connect to the relays at all: a fixture refuses every `wss://` connection unless `LIVE_RELAY` or `DEPLOYED_URL` is set (in Playwright's Windows WebKit, a host page's relay connections held up its companion socket for seconds). The separate **Live relay guest tests** workflow runs them weekly (Mondays), on demand and when its file changes.

Responsiveness under load (2.41): `SoundpadWeb.Harness.exe --playback-bench --slow-work [--transcribe-burn-ms N]` runs the 2.35 playback bench against the mock with keep-pitch copies, previews, Mimic recording with simulated recognition load and Panic presses, and reports how long the receive loop was held and how fast Stop and Panic were answered.

Capacity (2.45): `tests/e2e/capacity.spec.ts` joins 1, then 4, 8 and 12 guest pages to one host page against the mock Soundpad. In 8 rounds of a second, every guest presses Play and asks for the play counts (`statistics`) at a random moment, all at once, and the spec writes p50/p95 of click-to-start (a guest's Play until the companion answered that it started) and of the query to `test-results/capacity-<browser>.json`. Guests reach the host over the dev server's in-browser stand-in for WebRTC, every page shares one browser on one PC, and the mock answers at once, so these are the costs of the host page and the companion, not of networks or of Soundpad. Measured on the owner's PC (2026-11-15):

| Guests | Chromium play p50 / p95 | Chromium query p50 / p95 | WebKit play p50 / p95 | WebKit query p50 / p95 | Plays started (Chromium) |
|---|---|---|---|---|---|
| 1 | 65 / 83 ms | 27 / 60 ms | 110 / 143 ms | 61 / 92 ms | 8 of 8 |
| 4 | 65 / 106 ms | 33 / 110 ms | 112 / 175 ms | 80 / 118 ms | 31 of 32 |
| 8 | 76 / 116 ms | 68 / 217 ms | 141 / 195 ms | 110 / 297 ms | 55 of 64 |
| 12 | 76 / 130 ms | 122 / 286 ms | 205 / 607 ms | 226 / 471 ms | 65 of 96 |

Plays not started were replaced by a newer play from someone else before they reached Soundpad (the newest click wins, 2.35); none was refused. Click-to-start barely moves up to 12 guests: plays coalesce in the Bridge and have their own budget. Queries grow about linearly, because every play makes every page ask for the counts again (after a 250 ms pause). The first run found the real limit: with 12 guests, 5 of 96 queries were refused with "Too many requests", because all relayed guests shared the host page's 32 queries a second on the companion socket. Since 2.45 each relayed guest has its own 16 a second (`LocalServer.GuestQueriesPerSecond`; a host page already holds each guest to 12, paced at 8), and the run above refused none. That is why the cap stays at 12 places (`MAX_PLACES`, plus `MAX_EXTRA` granted on request): at 12 everything is answered and p95 stays under a third of a second in Chromium, while query time and the host page's work grow with each guest, so a larger room is not offered until it is measured on real networks with a real Soundpad.

Flaky tests, root causes (2.45): "Stop wins" (40 ms Soundpad) failed under load because the mock's sounds last 2.5 s: when more than that passed between the burst and the Stop click, nothing was playing, the guest's Stop was disabled and the click waited out the test; it now runs with `--sound-ms 60000` (harness flag: every library sound plays that long). The WebKit Mimic drag ("host listens …", whose clips show in Just mimicked) failed because a waveform asked for while following live could arrive after a drag had held the view still and move the window, so the second press missed the selection's edge; `viewStillWanted` (`web/src/mimic/history-poll.ts`) now drops such a reply. The Mimic hotkey test's flake was a toggle pressed while the previous command still ran, fixed in 2.19 (`727a70b`, it waits out `aria-disabled`); it did not reproduce in 42 stress runs here.

Diagnostics (2.45, gate `diagnostics`): error notices carry technical details (`web/src/technical-details.ts`, `components/TechnicalDetails.tsx`; folders are hidden on a guest's page). A host page sends its Activity (notices and guests joining, leaving and waiting) to the companion (`web/src/activity-sync.ts`, ops `activityAdd` / `activityList` in `BridgeDiagnostics.cs`), which keeps the newest 200 in memory until it quits, so a reload brings them back; nothing is written to disk. Settings → Companion log shows the end of `companion.log` (`diagnosticsLog`, host only, optionally with folders and the Windows user name hidden).

Real-Soundpad probes (2.44 real-hardware proof; owner-approved, net-zero, refuse while the companion or VRChat runs or Soundpad is busy): `--real-slot-probe`, `--real-slice-audio-probe`, `--real-exact-playback-probe`, `--real-edit-copy-probe`, `--real-session-cleanup-probe` (End-hosting cleanup kept while paused or playing, done once stopped and quiet), `--real-responsiveness-probe [--seconds S] [--seed N] [--out file.json]` (the `--playback-bench --slow-work` load against the real pipe, with Soundpad's output captured by process loopback to check what played last) and `--real-import-timing-probe`. Each takes `--data-dir <folder in the temp folder>` for its files and throwaway companion data (`RealProbes.cs`), waits until Soundpad has stayed stopped for 2 s before removing a category, and checks Soundpad's list is exactly as before. Soundpad refuses paths of 260 characters or more, so keep `--data-dir` short. The older `--real-session-cleanup` runs on the companion's real data folder.

Sentences (2.42): matching is `companion/src/SentenceComposer.cs` (a seeded dynamic program over phrases of up to 8 words), rendering `SentenceRender.cs` (only library recordings, pauses and bleeps; nothing else can make sound), storage and validation `SentenceModel.cs`, and the ops `BridgeSentences.cs`; the website side is `web/src/library/sentences.ts` (pure rules), `sentence-store.ts` and `components/SentencesPanel.tsx`. Every sentence and palette op leaves the receive loop (`Bridge.Offloaded`) after its intent is reserved, and every render, encode, preview and kept-audio read runs on the AudioWorker (`Heavy`), with game renders one at a time and cancelled by a newer intent. Test seams: `Bridge.SentenceRenderHold`, `SentenceStore.SaveLimit`, `UseSentenceWriteLimit`. User guide: [SENTENCES.md](SENTENCES.md); protocol: [shared/protocol/README.md](../shared/protocol/README.md#sentences-and-the-speaking-palette-242).

The studio layout (2.43): `web/src/components/shell/` holds the app shell (`AppShell`, `TopBar`, `SectionNav`, `SectionHeader`, `SectionView`, `EditorPanel` with `Splitter`, `SoundEditor`, `ActivityView`, `HeaderRibbon`, `Landing`, `DemoBanner`); `shell.ts` carries editor and view requests as window events (`requestEditor`, `showView`), `sections.ts` remembers each section's place, and `prefs.ts` / `motion.ts` keep the appearance choices. The header ribbon is `web/src/ribbon/` (`envelope.ts`, `machine.ts`, `draw.ts`; pure, unit tested). Host style sync is `web/src/ui-sync.ts` with the companion's `UiPrefs.cs` (`<data>\ui.json`, version 1, at most 4 KiB, strictly validated input, unknown keys kept, written through a temporary file) and `BridgeUi.cs` (`uiPrefsGet` / `uiPrefsSet`, host only, raising the snapshot's `uiRevision`). The Kick session count is `counterSession` in the snapshot, kept in memory. Edited and speed copies take a `TrimSource` (`{ assetId }` for Temp audio or `{ soundId }` for any Soundpad sound, `BridgeTrim.cs`). The example (`web/src/demo/`) reports companion `DEMO_COMPANION` and answers every command the website sends up to that version; `tests/unit/demo-coverage.test.ts` checks it, so raise `DEMO_COMPANION` only together with the example's support for the new commands. `tests/unit/demo-engine.ts` drives the example's model in unit tests. Shared e2e steps are in `tests/e2e/helpers/` (`harness.ts`: the fixture, which refuses public relays and adds every page's notices to a failure; `shell.ts`; `playback.ts`). `tests/shots/` holds manual screenshot and ribbon performance probes (`playwright.shots.config.ts`); they assert nothing and are not part of CI.

Stage H (2.44): backups, the updater, Organize mode and setup with host-wide hotkeys, each in its own files and described in its own document ([BACKUPS.md](BACKUPS.md), [UPDATES.md](UPDATES.md), [ORGANIZE.md](ORGANIZE.md), [SETUP.md](SETUP.md)).

- **Companion.** `BridgeStageH.cs` is the one place the four packages join the Bridge: `ExecuteStageH` asks backups (`BridgeBackups.cs`), updates (`BridgeUpdates.cs`), Organize (`BridgeOrganize.cs`) and setup (`BridgeSetup.cs`) in that order, and the first that knows the op answers. `StageHStarted` starts them once per process (at the top of `StartupCleanup`, from `ResumeFromHandoff` after an update, or from the harness), and registers the cross-checks: an update is refused while a whole-library restore or an Organize apply runs, and both refuse while an update installs. Backups: `Backups.cs`, `BackupSnapshot.cs`, `BackupRestore.cs`, `BackupSettings.cs`, `OfflineRestore.cs`. Updates: `Updater.cs`, `UpdateRelease.cs`, `UpdateSwap.cs`, `UpdateHandoff.cs`, `UpdateModels.cs`, and `companion/update-fixture/` (a console app that stands in for a new version in the swap test). Organize: `Organize.cs`, `OrganizePlan.cs`, `OrganizeApply.cs`, `NativeTree.cs`, `MissingFiles.cs` and `QuietRule.cs` (the stopped-plus-one-quiet-second rule, shared with the Temp category's removal). Setup: `SetupState.cs`, `SoundpadDiagnosis.cs`, `HotkeyChord.cs`, `HostHotkeys.cs`. Every Stage H op carries its details in the command's `body`, checked strictly by its own handler.
- **Website.** `web/src/stage-h.ts` provides the shell's state, controller, mode and notices to every Stage H piece (`useStageH`) and `organizeActive`. The pure modules are `backups.ts`, `updates.ts`, `organize.ts` and `shortcuts.ts`; components live in `components/backups/`, `components/updates/`, `components/organize/`, `components/setup/` and the Settings sections in `components/settings/`. `network/session.ts`'s `withoutHostOnly` strips the host-only snapshot fields (`backups`, `update`, `soundpadProblem`, `companionElevated`, `hotkeys`, `setupDone` and Mimic's F6 status line) for guests.
- **Companion options.** `--restore-state "<snapshot folder>" [--data-dir <dir>]` (offline restore of `state.json`; refuses while a companion holds the data folder), `--update-source <http(s)://127.0.0.1:port/ or [::1]>` (a local test release server; nothing else is accepted), `--no-hotkeys` (register no host-wide hotkey, for smoke runs), and `--launch-file <path>` with `--dev` (writes the launch URL for test clients, since the token is never printed). `--resume-update <id> --wait-pid <pid>` is internal: the old process passes it to the new one. CI publishes the release EXE with `-p:UpdateRepository=<owner/repo>`; any build without it says "This build doesn't update itself".
- **Harness.** Lines on its standard input run verbs (`HarnessStageH.cs`; any other line still ends it): `restart-history`, `update-exit`, `update-state <state> [version] [reason]`, `library-mutate <json>` (`addCategory`, `removeCategory`, `renameCategory`, `addSound`, `removeSound`), `remove-file <name>`, `reject-prefix <text>` (empty clears), `soundpad-offline`, `soundpad-online` and `press-hotkey capture|panic|stop`; e2e tests send them with `harness.send(line)`. Flags: `--backup-roundtrip <temp folder>` (back up a fixture, delete and damage it, restore, compare bytes; CI runs it), `--backup-hold-ms N`, `--handoff-out` and `--resume-update` (an update between two harness runs on one `--data-dir`), `--missing-fixture`, `--organize-duplicates` and `--first-run` (without it the harness writes a finished `setup.json`, so other tests never see the guide). Every harness gets a made-up Soundpad settings folder and suggested backup folder beside its temp data folder, fixture hotkeys (`Ctrl+Alt+F9` acts as a key another app owns) and a switchable "Soundpad is running" check. `--make-rollback-fixture` also writes every Stage H file.
- **Test seams.** `Bridge.UseLeppsoftFolder` (one Soundpad-folder seam for Organize's checkpoint and the backup folder rules), `UseSuggestedBackupFolder`, `UseBackupClock`, `UseBackupFiles`, `UseFileExists`, `UseBeforeOrganizeCommand`, `OrganizeQuietMs`, `OrganizeRemoveWaitMs`, `OrganizeApplyIdle`, `MissingScanIdle`, `RescanMissingFiles`, `UseHostHotkeys`, `UseSoundpadRunning`, `BlockUpdatesWhile` and `UpdateBusy`. `HostHotkeys.ForbidWindowsHotkeys` is set by a module initializer in the test assembly and by the harness, so no test can register a real Windows hotkey. MockSoundpad has `NestedIndexing`, `DuplicateOnAdd`, `InsertPositions`, `RemoveCategoryScope`, `ApplyLagReads`, `ExitOnRiskyRemoval`, `BeforeCommand` and a forbidden-command list (`DoSelect*`, `DoRemoveSelectedEntries`, `DoUndo`, `DoRedo`, `DoSaveSoundlist`, recording, search and scroll commands) that every test's teardown checks with `AssertNoForbiddenCommands` unless it opts out.
- **Process-level update test.** `scripts/update-swap-test.ps1 -Exe <published SoundpadWeb.exe>` (Windows PowerShell 5.1) publishes a "new" build (version + 1) into a temp folder, serves it from a TcpListener release server on 127.0.0.1, drives `updateCheck` and `updateInstall` over the loopback WebSocket and checks the swap, then wrong hash, truncated, wrong version, failing test run and never-ready versions, each of which must bring the old EXE back on the same port and token. It runs headless (`--no-window --no-browser`, and once `--hidden-window`) against a `--mock-only` harness pipe; CI runs it after the smoke test.

Stylesheets load in this order from `main.tsx`: `tokens.css`, the DM Sans font (`@fontsource-variable/dm-sans`, self-hosted), `studio.css` (the older rules, consolidated), `controls.css` (shared controls and focus), `mimic.css`, `voices.css`, `sentences.css`, `shell.css`, `playback.css`, `surfaces.css`, then Stage H's `backups.css`, `updates.css`, `organize.css` and `setup.css`. Each later file overrides earlier ones at equal specificity; the comment at the top of each says which components it owns. Keyboard focus is kept clear of the notices, the player and the phone sheet's bar by scroll-padding that counts `--player-height` and `--notice-height` (published by `Player.tsx` and `Notifications.tsx`), and clear of the phone's sticky header and a dialog's sticky title row by scroll-padding-top that counts `--topbar-bottom` and `--dialog-title-height` (published by `TopBar.tsx` and `Modal.tsx`), with `web/src/focus-clear.ts` as the safety net for what scroll-padding cannot reach (it also counts Review changes' sticky footer and the stuck Organize bar). A control that takes itself away (Remove, Discard, Later, Done organizing) hands focus on with `followFocus` (`web/src/focus-follow.ts`), never to the page.

Advanced companion options: `--site <HTTPS URL>`, `--no-browser`, `--no-window` (2.35 behaviour: a console and the default browser, whose tab hosts), `--hidden-window` (the window and its WebView2 run but are never shown; for automated checks on a PC someone is using), `--data-dir <local directory>`, `--pipe <test pipe name>`. `--dev` permits HTTP only for a loopback website. No LAN listener, firewall changes or system service is installed.

Since 2.36 the EXE is a desktop app (WinExe): closing its window quits it with the usual cleanup. Started from a terminal it writes there, and Ctrl+C stops it; Enter stops it only when standard input is a pipe (scripts, `scripts/smoke-exe.ps1`) or the console it opens itself in `--no-window` mode. Output is also written to `<data>companion.log` (rotated at 1 MiB). The window remembers its place in `<data>window.json`, and WebView2 keeps its profile in `<data>webview2`. The window page is the session owner: it gets a per-launch owner key in its link (never saved) and the companion keeps the host identity in memory, so a reload keeps the invitation. Other host pages are views. The harness accepts `--owner-key <64 hex>` to stand in for the window in e2e tests. Only one companion may use a given data directory at a time. `--licenses` prints embedded notices without starting a server. Native runtime dependencies are pinned to .NET / ASP.NET Core 10.0.13; update that patch and the bundled notices together when maintaining a fork. NuGet and npm lockfiles are checked in.

## Publish your fork with GitHub Pages

1. Put this source in your GitHub repository and enable Actions.
2. In **Settings → Pages**, choose **GitHub Actions** as the build source.
3. Push to `main` or `master`, or run **GitHub Pages** manually. Its final deployment step reports your actual URL.
4. Download the Windows workflow artifact and launch the EXE. The workflow embeds the default project Pages URL. For a custom domain or user/organization Pages repository, set the repository variable `SOUNDPAD_WEB_URL` to the actual website URL before building, or override it with the companion's `--site` option.

The deployment workflow derives the correct repository base path from Pages configuration, including project pages and custom domains. Local builds use relative asset paths by default. Override `VITE_BASE_PATH` only when needed. Push a `v*` Git tag to build, test and publish an EXE release with a SHA-256 hash. Source builds may embed a default website using `dotnet publish ... -p:WebsiteUrl=https://your-site.example/`; the runtime `--site` override always remains available.

## Network notes

Public [Nostr relays via Trystero](https://trystero.dev/) establish the connection; encrypted WebRTC carries commands/state. No application signaling server is deployed. Public relays are best effort, and restrictive NAT/firewalls may prevent direct WebRTC. No free universal TURN service is assumed. Advanced maintainers may configure their own TURN server at build time using `VITE_TURN_CONFIG` (JSON array of RTCIceServer entries). Anything embedded in a static bundle is public: never put confidential or long-lived third-party credentials there. Use credentials intended for public clients, or your own short-lived credential provisioning outside this project's normal setup.

## Where data is kept

Counter, permissions, statistics, icon references and an opaque-identity key live in `%LOCALAPPDATA%\SoundpadWeb\state.json`. Icon images live beside it in `icons/`; waveform caches live in `waveforms/`. Managed uploads/reversed WAVs and the schema-3 recovery journal live in `managed-audio/`; permanent copies default to `library/` beside it. Since 2.41 `library/` also holds the voice library: `voice-library.v1.json` (the previous version is kept as `voice-library.v1.bak.json` on each save; a save that would exceed 64 MiB is refused), `voice-words.v1.jsonl` (recording words), `voice-audit.v1.jsonl` (who changed what; rotated to `voice-audit.v1.old.jsonl` past 32 MiB) and `sound-words.v1.jsonl` (the category word index, keyed by path, size and modification time). They are separate from `state.json` and the journal, whose formats did not change. Since 2.43 `ui.json` beside `state.json` holds the host's shared style and open Mimic draft (see above); a missing, damaged or oversized file reads as the defaults and is left on disk until the next change replaces it. Since 2.42 `library/` also holds sentences: `sentences.v1.json` (sentences with their versions, named palette pieces and performance sets per person; strictly validated on load and before every save, written through `.tmp` and `File.Replace` keeping `sentences.v1.bak.json`, a save over 64 MiB refused, a damaged main file falling back to the backup and both damaged blocking all writes) and `sentences/<id>/v<N>-<hash8>.wav` (each kept version's audio, written once, its SHA-256 recorded in the version). `state.json` and the journal are again unchanged. Since 2.44 the data folder also holds `backup-settings.v1.json` and `backup-workspace.v1.json` (backups themselves go to the folder the host chose), `update-settings.v1.json` (plus `update-handoff.v1.bin`, DPAPI-protected for the current user, `update-ready.<id>` and `update-child.log` only during an update; a normal start deletes them), `organize\` (`plan.v1.json`, `settings.v1.json`, `checkpoints\`), `setup.json` and `hotkeys.json`; each is versioned, size-limited, strictly validated and written through a temporary file; a damaged settings file is left untouched and read as off or not done, and a damaged organization plan is set aside as `plan.v1.corrupt-<time>.json` and reported. Beside the EXE, an update leaves `SoundpadWeb.previous.exe`. Guest browsers keep their identity key in IndexedDB (`soundpad-web-keys`, store `keys`, record `guest-v1`; the private key is non-extractable). Legacy `session-audio/` records are backed up before migration. Previously accepted legacy files are preserved until the host confirms durable promotion; do not manually delete them. Small settings are saved atomically; unreadable data stops startup instead of silently resetting your counter. Browser refresh retains the session within the same host tab. Restarting the EXE or ending the host tab starts a new invitation session. Other people's hosts have separate state and secrets.

## Technical notes and limitations

See [vendor API research](API-RESEARCH.md), [protocol/security design](../shared/protocol/README.md), and [test evidence](VERIFICATION.md).

Icons follow an HMAC of the vendor file URL and duplicate occurrence. Unique paths survive reordering; moving/renaming a file changes identity, and exact duplicate paths cannot be perfectly distinguished. Soundpad does not offer an atomic persistent-ID play command, leaving a narrow last-query/play reorder race. Now-playing titles are deliberately not guessed from the last browser click: manual Soundpad playback remains usable.

With `--no-window` (or without the WebView2 Runtime), browser background throttling or a suspended host tab can interrupt hosting, and the EXE does not independently maintain WebRTC when the host tab is closed. HTTPS-to-loopback policies vary by browser; passing local HTTP tests is not proof of GitHub Pages compatibility. The EXE is unsigned; this project does not install a certificate or modify your system trust settings.
