# Protocol 1

The executable and website must agree on `v: 1`. Types and strict guest-command schemas live in `web/src/protocol.ts`; native records and validation live in `companion/src/Models.cs` and `Bridge.cs`.

Loopback: `ws://127.0.0.1:<ephemeral port>/bridge`. Require the exact configured website Origin and numeric loopback Host, then `{token}` within five seconds. No token in WebSocket URLs. One host tab owns the bridge. Requests are `{actor,command}`. Only this authenticated browser can set `actor: host`; relayed commands always use the fixed guest actor, regardless of a peer-provided identity. The native bridge independently enforces guest permissions. Replies are `{type:"ack",id,ok,error}`; snapshots are `{type:"state",state}`. Maximum inbound frame aggregate 200,000 bytes, 20 requests/second, serialized queue at most 24.

Commands: `{v,id,at,op,...}`. UUID `id`, UTC Unix milliseconds `at`. Allowlist: `play`, `stop`, `counter`; host-only `reset`, `permissions`, `icon`, `refresh`. `play` requires `soundId` and `libraryVersion`; `counter` requires `delta: -1 | 1`. Reject playback older than five seconds and other commands older than 30 seconds, including after queuing. No retries for playback. Native persistent receipts deduplicate accepted IDs for at least two minutes. Fresh UUID per intentional action. A repeated accepted ID acknowledges without applying again. An expired retry is rejected, never reapplied. Queue overflow rejects immediately.

Guest transport: Trystero 0.26 Nostr strategy. Random 192-bit room and 256-bit password, unique per host session. Invitation fragment carries `{v,room,secret,publicKey}` only. It does not carry the native token or signing private key. Host browser keeps its ECDSA P-256 signing key in sessionStorage so a same-tab refresh can recover. Starting the executable again creates a new native token and new browser session identity.

Peer discovery alone is not authentication. Guest sends `hello` with a random nonce. Host sends `welcome` with a signature over JSON `[1,room,nonce,hostPeerId,guestPeerId]` plus the initial snapshot. Guest pins the invitation public key and accepts later state, ACK and revoke messages only from the peer that verified this signature. Guests cannot impersonate the host using the shared room password. Acknowledgments are application-level; Trystero send completion alone is insufficient. Each host authenticates up to 12 guests. Per-peer 12 message/second limit (host receive); malformed commands close/deny the peer. Incoming guest payloads are capped at 8 KiB before transfer; guest snapshot receive budget 16 MiB.

State revision orders snapshots. Full library is sent on welcome and library-version changes; `tick` carries lightweight authoritative state and a library version, with a full resync on mismatch. Counter and permissions live in the companion; no guest localStorage authority. Library refresh every 30 seconds, playback status every two seconds, library revalidation immediately before play. Polling and commands share the native serial gate. Playback identity is intentionally not guessed: Soundpad's documented status API does not reliably identify manually initiated current tracks.

Disconnect uses an in-memory denied-peer list and closes that connection. Since an invite is a bearer credential, a person can rejoin with a new browser identity until the host **replaces the invite**. Rotation revokes current peers, leaves the room, creates new cryptographic material, and preserves local counters/icons. Old invitation refreshes may show Host unavailable rather than Access revoked if they missed the explicit revoke message.

This is a small-room mesh, not a large broadcast service. Public relay availability, browser background suspension, NAT/firewalls and browser loopback policies can prevent connections. No hosted application backend, custom signaling server, audio relay, or cloud database exists.

## Playback intents (2.35)

The paragraphs above describe the original protocol; these rules replace the ones they contradict.

- **Intents.** `play`, `startAt`, `region`, `audioPlay`, `reverse`, `stop`, `panic`, and `trimAudio` / `mimicClip` / `mimicLibraryImport` sent with `autoplay: true` are playback intents. The companion numbers them in the order they arrive (never by client clocks) and only the newest may start audio. A superseded, expired (older than 5 s; 30 s for `stop`, `pause`, `panic`) or suspended intent is acknowledged `{ok:true, data:{superseded:true, reason:"newer"|"expired"|"suspended", played:false}}`. It is never an error and never plays later. `seek` and `pause` are bound to one playback (`soundId` + `epoch`); for a playback that is gone they are acknowledged `{superseded:true, reason:"stale"}`.
- **Started plays** are acknowledged `{played:true, epoch}`. An `autoplay` command returns its usual data plus `played`.
- **`panic`** (host only): `action:"enable"` stops Soundpad, cancels pending starts and sets the snapshot's optional `playbackSuspended`; `action:"disable"` clears it. While set, guest playback input gets the quiet `suspended` answer. In memory only.
- **Stop and Panic** do not take the native gate; they wait only for the pipe request in flight. Starts hold the gate in an urgent lane, and a start still waiting when a newer intent arrives leaves the queue at once.
- **Durability.** Counter, permissions, icons and settings are on disk before their acknowledgement. Receipts, statistics and activity of plays are written by a background flush about 300 ms later and on clean exit.
- **Loopback limits.** Nothing is awaited in the receive loop. Playback/control ops (`play`, `startAt`, `region`, `stop`, `seek`, `pause`, `panic`, `audioPlay`, `reverse`) have their own bucket of 600 per second; everything else keeps 32 per second and the 16-slot limit for slow work.
- **Coalescing.** Stops that arrive together share one `DoStopSound`. A seek waiting for the gate is replaced by a newer seek; a second pause is answered as stale while one waits. The loopback socket gives the host's own control ops a separate bucket, and the host page counts unanswered control commands per sender (64 per guest, 512 for the host).
- **Guest limits in the host page.** With a 2.35 companion, per guest and per second: 100 control ops, 12 other messages (refused with an acknowledgement, the guest stays), and 400 in total before the guest is dropped. With an older companion every guest message shares the 12 per second, as in 2.34. On a guest page only the verified host is exempt from the flood cut-off. Malformed traffic still drops; a well-formed command with an unknown op or field is refused with "The host's page is older than yours".
- **Versions and clocks.** `hello` and `welcome` carry the page's website version as `site`; a guest sends no op or field newer than the host page knows. Every `state` and `tick` carries `hostNow`, from which the guest keeps its clock offset current.
